# duplicate-statements：改代码时只加不删，输入被读了两次

- **日期**：2026-10-14
- **出处**：`01-textbook/control/change_maker.c`
- **关键词**：复制粘贴、漏删、scanf、回归

## 现象

给 `scanf` 加上返回值检查时，**忘了删掉原来那句**：

```c
9:        scanf("%d %d", &price, &pay);              /* 旧的，忘了删 */
11:       if (scanf("%d %d", &price, &pay) != 2)    /* 新的 */
```

结果程序**每轮要读两次输入**，第二次的值覆盖第一次。

测试暴露得很清楚：

```text
$ echo "37 100" | ./change_maker
请输入应付金额 实付金额:输入无效，程序结束
退出码=1                          ← 正常的输入被判成非法！

$ printf "37 100\n37 100\n" | ./change_maker
请输入应付金额 实付金额:应收: 37 元      ← 输两遍才工作
```

最坑的是**在 VS Code 里看不出来**：输完 `47 10` 回车后，屏幕不报错也不提示，就是静静地等——你得再输一次它才动。看着像"卡了一下"，其实是在等你输第二遍。

## 原因

改代码时的本能是「把新东西加上去」，而不是「把旧东西换掉」。

尤其是**加保护性代码**的时候很容易这样——心里想的是「多一层检查更安全」，手就只做了加法。

编译器不会救你：两句 `scanf` 语法都合法，第二次覆盖第一次也是合法行为，`-Wall -Wextra` 一声不吭。

## 教训

改完代码，**不要只看新加的那几行**，回头把整个逻辑流从头读一遍：

1. 输入从哪来、读了几次？
2. 每个变量最后一次被写是什么时候？
3. 这个分支进去之后，会走到哪一行？

最快的办法是**用调试器单步走一遍**（`F10`）。肉眼看十遍不如 `F10` 走一遍——因为单步会把**真实的执行顺序**摆在你面前，而看代码看到的是**你以为的顺序**。

**一句话记住它**：

> 加代码之前先问：我是在**补充**，还是在**替换**？如果是替换，旧的必须删掉。
